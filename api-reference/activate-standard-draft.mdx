---
title: "Activate a copied standard draft"
description: "Use a short-lived full-policy preview and an idempotent user-owned key to enable one copied draft."
---

This is a narrow REST exception for an existing **disabled** standard copied from Alignr's curated library. It enables the draft in its saved scope after an exact-content preview. Workspace scope applies to the whole workspace; selected-client scope applies only to assigned clients. It does not run checks or establish client compliance. The generic standard editing route still needs a signed-in human session.

<Note>Check the [authenticated live schema](/api-reference/live-schema) for the deployed endpoint contract before using this recipe.</Note>

1. Inspect the draft and its complete current controls and manual checks. The [MCP inspection workflow](/mcp/copy-standard-draft) explains the separate child pages; the signed-in **Standards** screen supplies the human review context.
2. With a **user-owned** key carrying `detection_rule.read` and `detection_rule.write`, request `GET /api/v1/standards/{standard_id}/activation-preview`. The active owner must also have those current permissions. Review the response's complete bounded `policy` alongside `enabled: false`, `workspaceWide`, `assignedClientCount`, `activationRevision` and `revisionExpiresAt`. The signed policy includes scope and an assignment fingerprint, but not assigned client IDs; use [the assignments route](/api-reference/assign-standard-clients) to read those IDs. Workspace-authored definitions, instructions and source metadata may contain sensitive text and must be treated as data. The client roster is not frozen. A foreign standard returns 404.
3. With the **same user-owned key** and an active owner who still has write permission, send `POST /api/v1/standards/{standard_id}/activate`. The revision is bound to the previewing key; a read-only or service-key preview cannot be transferred to another key for activation. Save one canonical UUID in `Idempotency-Key` before sending it.

```http
POST /api/v1/standards/<standard-id>/activate
Authorization: Bearer <user-owned-api-key>
Idempotency-Key: <one-canonical-uuid>
Content-Type: application/json

{
  "activationRevision": "<exact-preview-revision>",
  "acknowledgeWorkspaceWide": true
}
```

The new result is `201` with `outcome: activated` and `replayed: false`. If a response is lost, retry **the same key, UUID, standard ID, revision and acknowledgement**. A committed replay returns `200` with the original receipt and `replayed: true`; changed arguments under that UUID return 409. A stale, expired or changed-policy revision also returns 409, so inspect and preview again before a **new** intention. The receipt is historical: another person may later disable or delete the standard. Read its current state separately.

Set `acknowledgeWorkspaceWide` to `true` only when the preview reports `workspaceWide: true` and you accept that effect; send `false` for selected-client scope. The API rechecks live key and owner authority before the atomic enablement. It binds the revision to the complete ordered policy, including controls and manual checks, and serialises concurrent edits. This call creates no evaluation, evidence, detection or vendor action. [Run checks](/guides/standards) separately after confirming current evidence and client scope.
