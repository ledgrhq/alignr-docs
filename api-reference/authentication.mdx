## Bearer authentication

```http
Authorization: Bearer <your-api-key>
```

[Create an API key](/guides/api-keys) with the scopes required by a key-compatible operation. Many REST scopes use permission codes such as `organization.read` and `detection.read`; MCP tools use the names in the [tool reference](/mcp/tools). The exact-plan review REST routes below accept the same colon-named scopes as their corresponding MCP tools.

An API key scope grants permission only where the route accepts API keys. User-owned keys with `organization.write` can call `POST /organizations`, `PATCH /organizations/{organization_id}` and `DELETE /organizations/{organization_id}` to [manage clients](/api-reference/manage-clients-recipe). Service keys cannot call those client writes, even when they carry that scope.

The exact-plan REST review routes are another explicit key-compatible exception. A user-owned key with `remediation:preview` can call `GET /api/v1/remediations/plans/{plan_id}/review-preview` with the `detectionId` query parameter. A user-owned key with `remediation:request` can call `POST /api/v1/remediations/plans/{plan_id}/review-requests` with JSON `detectionId` and `reviewRevision` plus a caller-generated UUID in the `Idempotency-Key` header. These colon-separated scopes also serve the corresponding MCP tools; they are not a general REST write grant. The active key owner needs current `remediation.read` for preview and both `remediation.read` and `remediation.execute` for request, with no required password change. Service keys are refused. A new request creates only a pending run and human approval, never an execution. Follow the [review-request workflow](/mcp/request-review) for the revision and uncertain-result rules.

The [evidence refresh routes](/api-reference/refresh-evidence) are also key-compatible. `POST /api/v1/integrations/{integration_id}/sync-operations` accepts a user-owned key with the REST scope `integration.manage`, a currently permitted owner and a canonical UUID `Idempotency-Key`. Its matching GET uses `integration.read`; a read-only service key may poll but cannot start a refresh. The corresponding MCP tools use the distinct `integration:sync` and `integration:read` scopes. A refresh covers the entire connection, not one client.

The [source-client linking routes](/api-reference/link-source-clients) are another narrow exception. A key with REST `integration.read` can discover existing PSA/RMM mappings; a **user-owned** key with REST `integration.manage` can first-link one unassigned mapping to an existing client using a fresh revision and canonical UUID `Idempotency-Key`. A service key may read, never link. MCP uses `integration:read` and `integration:map` instead; `integration:map` alone does not permit `integration:sync`. The first-link operation does not itself create clients, refresh evidence, change a Microsoft connection or grant arbitrary mapping edits. REST `integration.manage` separately permits the supported source-refresh POST route.

The curated standards-library routes are a further narrow exception. A key with `detection_rule.read` can list and read templates with their current `revision`; a **user-owned** key with `detection_rule.write` can call `POST /api/v1/standards-library/{key}/copy` with `expectedRevision` and a canonical UUID `Idempotency-Key` to copy that exact template into a disabled draft. A service key cannot copy. The [MCP draft-copy guide](/mcp/copy-standard-draft) explains safe same-key recovery; MCP uses the separate `standards:read` and `standards:copy` scopes.

The [copied-draft activation routes](/api-reference/activate-standard-draft) add one bounded exception. The summary, pages and legacy full-preview GET routes accept `detection_rule.read`; use the summary and pages to review large policies without a total row ceiling. `POST /api/v1/standards/{standard_id}/activate` accepts a **user-owned** key with `detection_rule.write` and the exact short-lived revision from the same key's review. Provide workspace-wide acknowledgement only when the summary or legacy preview reports workspace scope. Use a canonical UUID `Idempotency-Key`. Service keys cannot activate. MCP uses the distinct `standards:read` and `standards:activate` scopes. Activation alone does not evaluate clients or prove compliance.

The [one-client evaluation routes](/api-reference/evaluate-one-client) are another explicit exception. A key with REST `detection_rule.read` can preview one enabled standard and client and poll the exact operation. A **user-owned** key with `detection_rule.write` can submit the short-lived, same-key preview revision with an explicit client and canonical UUID `Idempotency-Key`. The client must be within the standard's saved scope; use [standard assignments](/api-reference/assign-standard-clients) to read or replace selected-client applicability. A service key may read but cannot request evaluation. MCP instead uses `standards:read` and `standards:evaluate`. An evaluation request does not refresh evidence, assess manual checks or change standard assignments.

Other REST writes, including direct standard creation, general editing and detection mutations, still require a signed-in human session. Issuing another write scope does not by itself make its route callable with a key.

## User and service keys

A user-scoped key’s effective permissions are intersected with its owner’s current permissions on every request. Client writes also require an active owner who is not required to change their password. Revoking the key, deactivating its owner or removing `organization.write` from the owner removes write access. Service keys have assigned scopes and require an expiry, but are refused for client writes.

## Tenant scope

Your credential identifies the tenant: your MSP workspace. Supplying another tenant’s Organization or resource ID does not grant access. Resources outside your tenant are treated as not found.

## Human authentication

The application also uses short-lived session tokens. In the [Developer Console](https://app.alignr.io/developer), choose **My session** for operations that require a signed-in human. Some sensitive actions require additional verification. Step-up authentication is an extra verification step for sensitive actions. An API key does not replace it and cannot obtain a secret-reveal step-up token.

Use the authenticated [live reference](/api-reference/live-schema) to check the requirements for each operation.
