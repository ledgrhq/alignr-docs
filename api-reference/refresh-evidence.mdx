---
title: "Request an evidence refresh"
description: "Start source-wide or customer-targeted collection with an idempotency key."
---

These REST routes request and read an evidence refresh for one integration. The standard request covers **all clients mapped to that source**. Microsoft Partner Graph also has a human-only route to retry one already-mapped client. Both collect evidence; neither imports client records or promises a completed assessment.

For a run limited to one standard and selected clients, use [Run checks for selected clients](/api-reference/run-scoped-standard-checks). That workflow collects through sources mapped to those clients and then evaluates the named standard. Some sources may read an account-wide provider inventory, but only selected-client evidence is published and assessed by that run. It is separate from this connection-wide refresh.

Use a user-owned API key with `integration.manage` and an active owner who currently holds that permission to start a source-wide request. A signed-in human with `integration.manage` can also call it. Polling requires `integration.read`; a read-only service key can poll when granted that scope. A service key cannot start collection. The customer-targeted Partner route below is restricted to signed-in human REST callers; API keys and MCP callers cannot use it.

## Start a request

Generate a UUID once, store it with the source ID, and send an empty-body POST:

```bash
curl --fail-with-body -X POST \
  'https://api.alignr.io/api/v1/integrations/11111111-1111-4111-8111-111111111111/sync-operations' \
  --header "Authorization: Bearer $ALIGNR_API_KEY" \
  --header 'Idempotency-Key: 22222222-2222-4222-8222-222222222222'
```

Use your own source ID and canonical UUID, not the illustrative values. A new durable request returns HTTP `202` and an operation `id` with `state: pending`. A replay of the same caller, key and source returns HTTP `200` with the **current** operation state. Reusing the key for a different source returns `409`. The request can also be refused when the source is not connected, does not produce evidence, has no selected Microsoft client or already has an active refresh.

## Retry one mapped Partner customer

After reviewing a client's Microsoft Partner collection failure, a signed-in human with `integration.manage` can request a retry for that already-mapped client. The [integration mappings guide](/api-reference/integration-mappings) explains what the recorded failure fields establish.

```bash
curl --fail-with-body -X POST \
  'https://api.alignr.io/api/v1/integrations/11111111-1111-4111-8111-111111111111/sync-operations/organizations/33333333-3333-4333-8333-333333333333' \
  --header "Authorization: Bearer $ALIGNR_ACCESS_TOKEN" \
  --header 'Idempotency-Key: 44444444-4444-4444-8444-444444444444'
```

Replace both resource IDs and the key with values from your workspace. The key must be a canonical UUID. A newly accepted request returns `202`; replaying the same caller's key for the same source and client returns `200` with the original operation. Reusing that key for a different client returns `409`. The operation response includes `targetOrganizationId` so the durable request identifies its client. Successful responses use `Cache-Control: no-store`.

This route accepts only a mapped, active, selected client in your MSP workspace and only for a Microsoft Partner Graph source. A caller without `integration.manage` receives `403`. A missing, archived, foreign-workspace or unmapped client is hidden as `404`. A non-Partner source, a mapped client outside the source's selected customer set, a conflicting idempotency key, or another pending/running refresh for the source returns `409`.

The targeted request skips the source-wide Partner consent/grant preparation step; it does not initiate consent or grant preparation. It still collects only the selected client's evidence and does not advance the source-wide incremental cursor, including when that client is the only mapped client. This is a retry of a mapped customer, not a way to create a mapping or select a new Partner customer.

Poll the returned operation with the same `GET /api/v1/integrations/{integration_id}/sync-operations/{operation_id}` route described below. Collection completion remains distinct from assessment.

## Poll the exact operation

```bash
curl --fail-with-body \
  'https://api.alignr.io/api/v1/integrations/11111111-1111-4111-8111-111111111111/sync-operations/33333333-3333-4333-8333-333333333333' \
  --header "Authorization: Bearer $ALIGNR_API_KEY"
```

Replace the final UUID with the returned operation `id`. The source and operation IDs must match in your MSP workspace; a foreign or mismatched pair returns `404`. The response contains `id`, `integrationId`, optional `targetOrganizationId`, `state`, optional `sweepId` and `syncRunId`, `startedAt`, `finishedAt`, `errorCode` and `assessmentState: unknown`. Both routes use `Cache-Control: no-store` on successful responses.

`pending` means recorded, `running` means an exact SyncRun was claimed, and `completed` means that exact run finished evidence collection. `failed` and `interrupted` carry a safe `errorCode`; vendor error bodies and credentials are not returned. `assessmentState: unknown` means the operation does not attest that later detection or standards evaluation completed. A passing control requires current, applicable evidence and its own evaluation.

If the POST response is uncertain, retry with **the identical source and Idempotency-Key** before creating a new request. After the exact run is claimed, the server does not automatically replay uncertain vendor work. Use the poll route to recover the durable outcome. See [Refresh evidence with MCP](/mcp/refresh-evidence) for the state table and recovery guidance.
