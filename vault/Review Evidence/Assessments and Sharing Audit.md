## Prioritised concrete gaps and bounded fixes

### P1 — Complete a manual client review and follow up without mistaking task completion for a pass

The manual-check guide stops at recording one assessment. A reader entering **Client → More → Manual reviews** has no guide to the actual review queue, scheduling, batch scope, progress or follow-up. This is a major daily workflow, not a reference detail.

Add `guides/client-reviews` under an expandable **Review and follow up** group; link from manual checks and the close-the-loop journey. Teach **Start client review** (all manual checks due at creation), owner, due date and review period, then assess → pause/resume → handle changed items → complete. Explain the period labels the review; it does not filter due checks. Progress counts manual handled items and may include explicit skips; it is not alignment percentage, automated assessment coverage or pass rate. A batch cannot complete with pending items; completed reviews cannot resume (`review_batch_service.py:375–386`). Include single-check assignment and failed-assessment follow-up as concise sections, with a diagram `review due → record assessment → failure follow-up → work done → reassess`.

Permission prerequisites visible in source: client + rule read to view, client read + rule write to manage (`AssessmentWorkPage.tsx:119–120`). Do not imply creation of a follow-up records a new assessment, or that all estate client records fit in a single visible page. Existing statuses/version checks should be source-checked during authoring; no runtime queue exercised here.

### P1 — Prepare and share an actual client review report

Users have no instructions for the routed reports page. Add one focused `guides/client-reports`, linked from the final journey and manual review guide. Task: client **More → Review reports**, refresh/assess source evidence as needed, **Prepare review**, inspect date/generated time and gaps, **Print or save PDF** or **Export report data (JSON)**. Explain saved snapshots are fixed; improving the live environment does not rewrite a saved report. The source creates a snapshot at generation (`alignment_report_service.py:392–438`); no recurring/scheduled email report feature is evidenced.

Document read access depends on dashboard, client, rules, detections and roadmap read; creation additionally needs organization.write (`AlignmentReportsPage.tsx:16–22, 325–326`). Warn through a precise checkpoint, not boilerplate: exports carry client evidence, so review the intended recipient/scope. Do not claim portal preview and full internal report reveal identical information. A small example distinguishes `saved 26 Sep` from `current result 27 Sep`.

### P1 — Risk acceptance, proposal decisions and remediation are distinct operations

Neither risk nor roadmap workflow has public how-to coverage. The reader can see these product tabs but cannot learn their operational contract. Add a compact `guides/risk-and-roadmap` rather than separate pages for every dialog. Start from a detected risk: inspect evidence → accept temporarily with reason/expiry or **Create proposal** → review estimated cost and timing → internal decision → delivery → fresh evidence verification. Include manual failures as a separate evidence-review list, not an assertion that they have the same detection actions.

Source requirements: detection.write for acceptance, roadmap.write to propose/change, roadmap.read to view (`RiskActionsMenu.tsx:34–36`). Acceptance requires future expiry and reason (`risk_service.py:302–354`); decision history persists. A proposal is not acceptance/resolution (`PromoteDialog.tsx:111`). Roadmap costs separate one-off/monthly/annual (`RoadmapTab.tsx:405`); work completed records delivery and source risk closes only after verification (`:443`). Do not describe proposal approval as automatic execution. Include standalone roadmap items and unscheduled timing without inventing mandatory linkage to detections.

### P1 — Complete portal sharing, then teach the external client experience

Current settings/configure-client pages cover policy basics but leave **People & views**, explicit decision access and actual client sign-in disconnected. Add `guides/client-portal` for the MSP handoff, with a short clearly separated “What your client does” section (or a second viewer page only if the owner wants a shareable client-facing guide).

MSP progression: workspace hosting/address prerequisites → client Microsoft tenant and policy → people/grants → default/person view → independent proposal decision toggle → preview the intended audience → verify an authorised real external sign-in before distributing the address. Keep view selection distinct from permission to sign in and permission to decide. Existing `configure-client` correctly states tenant-wide policy is not revoked by removing one explicit grant; preserve it. Explain presentation exclusions do not switch off internal checks (`ExclusionsSection.tsx:74–80`). Hide costs/roadmap has consequences for proposal visibility; verify source before stating exact combinations.

External progression: provider portal `/portal` → **Continue with Microsoft** (`PortalSignInPage.tsx:44–46`) → callback → overview scoped to authenticated client's Organization; the staff session does not substitute (`PortalApp.tsx:10`, `main.tsx:5–8`). **Work awaiting review → Review proposal → Approve/Decline**, optional note. This records the client response and does not execute work or change internal MSP approval (`PortalProposals.tsx:97–102, 127–128`). If proposal changed or was already decided, close and reopen latest; if permission changed, ask provider (`:134–136`). **Sign out** clears local session, with honest server-revocation failure warning (`PortalSignInPage.tsx:21`, `portalApi.ts:189+`). No live Microsoft/portal host test conducted.

Media review: current authenticated external media path is logo display (`usePortalLogo.ts:14`); staff preview uses a different staff endpoint. Document upload/replace, inspect light/dark and verify external display under portal troubleshooting; do not invent a client attachment/document library or publication flow from unrelated retired files.

### P2 — Guided baseline and questionnaire import need a genuine starting-path comparison

Existing controls docs imply library copy/custom edit as the main starts while routed Guided setup and import only receive a setup sentence. Add a short choice table to standards/baseline overview: guided builder for choosing managed areas, library for reviewed template, spreadsheet import for existing human questionnaire, blank standard for bespoke work. Then one `guides/build-or-import-standard` with two task sections (or tabs if it stays readable), linked from setup. Keep reference catalogues separate.

Guided intake exact source: automated identity/endpoints/backup plus 15 manually reviewed areas (`BaselineIntakePage.tsx:16–38`); per-area instructions/cadence; local browser resume (`:239, 297–299`); Save baseline creates inactive standard (`:215`) → Review & enable baseline (`:314`). Distinguish a browser draft from saved standard, and record local storage unavailable recovery. Enabling standard applies workspace-wide with client exceptions (`:312`), not solely to a client selected earlier.

Import exact path `/standards/import`: `.xlsx` or UTF-8 `.csv`, 3 MB limit, 1–1,000 questions, Question column, optional Explanation/Category/Responses semantics (`assessment_import_service.py:38–65, 65–137`). UI says values only; formulas rejected rather than executed. Review included/skipped/split rows and rationale, separate cadence interpretation (especially Bi-Annual), save progress, create inactive standard only after all rows reviewed and at least one included. Imported questions become manual definitions, not answered assessments (`AssessmentImportPage.tsx:375–376`; service apply `:250–259`). Do not promise AI generation of automated predicates from spreadsheet questions. Provide a fictional minimal CSV with documented parser semantics after checking headers; no real customer questionnaires.

### P2 — The “all 19 supplied manual checks” phrase overstates catalogue scope

Committed `controls/manual-checks.mdx` closes with “all 19 supplied manual checks”. Those are the seven standard-library templates' manual checks; the currently routed guided intake has 15 manually configured areas and its own generated definitions (`BaselineIntakePage.tsx:21–38`, `intakeControls.ts`). Change to “the 19 manual checks in the standard-library templates” and cross-link the guided build route once documented. Likewise baseline overview should explain its inventory is seed/library content, not every way the product supplies a baseline. This is a factual scope clarification, not a request to bulk-publish every generated variation.

## Additional routed surface: Monitoring rules

The route reconciliation also includes `/monitoring`, `/monitoring/rules/new` and `/monitoring/rules/:ruleId` (`frontend/src/router.tsx:102–104`). These remain routed and must not be classified as retired merely because the source comments call the engine path legacy. No link to Monitoring was found in the current `AlignmentShell` or `SettingsPage`, so document it as an advanced directly routed surface pending owner confirmation of intended discoverability, not as an invented **Settings → Monitoring** menu path.

`frontend/src/features/monitoring/MonitoringPage.tsx:47–58, 168–188` lists detection rules with name, scope, monthly fired count, autonomy and enabled toggle; **+ New rule** opens the editor. Controls are labelled CONTROL and route to their owning standard instead of using this editor (`:28–42, 132–149, 184`). The standalone editor supports name/slug/description/severity/category, client scope, autonomy/enabled, match anchor with optional typed exact value, additional where conditions, title template and evidence fields; create/save/delete (`RuleEditorPage.tsx:145–208, 269–447, 498`). `RuleScopeField.tsx:75–111` explicitly separates Every organization (including future clients) from Selected clients only. Use an initially disabled rule for a teaching example and avoid representing a list filter as evidence of complete estate selection.

**P1 semantic gap:** public control definition pages do not teach that a standalone detection rule has opposite selection semantics from a standard control. For a standalone rule, matching match/where identifies a candidate violation; for a control, match/where selects population and expect defines what should hold (`api/ledgr/detection/engine.py:8–25`). Blindly transferring a compliant-population control definition into the rule editor can ask the wrong question. Add a compact “Controls versus standalone detection rules” distinction to `controls/advanced-definitions`, with an advanced rule guide only if this routed feature is meant to be publicly supported. Use an example of a known contrary observation, not a healthy selected population. The editor deliberately cannot represent control expect/parameter declarations and redirects standard-bound rules (`RuleEditorPage.tsx:128–140`). No universal JSON-import/editor promise belongs here.

The LLM-assisted toggle is visible for creation (`RuleEditorPage.tsx:198–208, 340–341`) and depends on runtime capabilities; do not promise its live availability based on the existence of a toggle. The source describes verifier gating before shown detections (`engine.py:1–4`). This read-only audit did not exercise evaluator dispatch, verifier/model availability, scope pagination or mutation permission enforcement. A follow-on author must verify precisely what is currently supported, including which settings are creation-only, before adding a tutorial.
