# Editorial standards

## Quality bar

A reader should know where to start, what to do, what success looks like and where to go when reality differs. Visual polish supports those outcomes. Do not claim awards or invent usability evidence.

## Writing

Use British English, with the established Organization label. Lead with the reader's task and outcome. Explain specialist terms on first use. Use readable observation labels before identifiers. Prefer one clear limitation beside the relevant claim over repeated defensive warnings. Every workflow must distinguish completing setup, collecting evidence, evaluating a control and performing an action.

## Examples

Use fictional Acme and the accounts Alex, Morgan and Sam consistently in the guided identity assessment. Mark examples as illustrative, never production records or exact API responses unless they are verified schema examples. Include satisfying, contrary, missing and empty-population cases where relevant. Verify thresholds at the boundary and check effective overrides.

Do not suggest synthesising production facts to make a result pass. A low count is not low risk, registration is not enforcement, presence is not health, and a successful backup is not a restore test.

## Visuals

Use small, vertical Mermaid diagrams for causal flows and decisions. Include a prose explanation and check mobile rendering. Tables compare parallel information. Tabs show alternative scenarios or separate explanation from definition; disable synchronisation when entries should be independent. Avoid charts without real data and decorative images that imply product functionality.

Screenshots must come from the actual current UI in an authorised, non-sensitive context. Record the source revision/date and inspect redactions. Do not publish simulated UI as a product screenshot. If no suitable workspace is available, retain accurate written instructions and record screenshot work as outstanding.

## Page patterns

- Journey: intended outcome → prerequisites → actions → checkpoints/recovery → next stage.
- Recipe: question → editor settings → boundary examples → limits → rollout.
- Concept: plain-language model → one worked example → technical detail → next action.
- Reference: purpose → topic grouping → exact entries with interpretation limits.

## Release review

Check source-backed claims, links, labels, mobile navigation, diagrams, code blocks and deep links. Run Mintlify validation and structural vault checks. Record what was tested and what remains unverified. Semantic product changes require source verification and example updates even when generated output is unchanged.
