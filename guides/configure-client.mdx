A client brings together one business's source records, checks, exceptions and follow-up. Start with its identity, then configure the evidence and expectations you will use to assess it.

This guide covers the current app workflow. If your source already contains the client, [import and link its record](/guides/organizations) instead of creating a duplicate.

## Add a client

Open **Clients** in the sidebar, then select **Add client**. Creating a client requires `organization.write`.

| Field | What to enter |
| --- | --- |
| **Name** | The client name your team should recognise. |
| **Seats** | The seat count you want recorded for this client. Enter zero or a positive number. |
| **Remediation limit** | The client's permitted level of action. New clients start at **Suggest only**. |
| **Advanced options → Slug** | The short identifier initially derived from the name; review it before saving. |
| **Advanced options → PSA reference** | An optional matching record ID from your PSA. |

Select **Create client**, then open the client from the list. Entering a PSA reference does not connect the PSA or establish its source mapping; [link the source records](/guides/organizations) separately.

**Checkpoint:** you have one client for the intended business. The record's existence does not mean evidence has been collected or checks have passed.

## Find the right setting

The available tabs and actions depend on your permissions.

| What you want to do | Where to go |
| --- | --- |
| Link tools and their client sites. | Client → **Connections**. |
| Review a client's Microsoft tenant access. | Client → **Connections** → Microsoft connection → **Client sites and access**. |
| Configure public DNS checks for client domains. | Client → **Domains**. |
| Inspect control results and coverage gaps. | Client → **Checks**. |
| Review recorded risks and planned improvements. | Client → **Risk register** or **Roadmap**. |
| Change control parameters or client exceptions. | [Standards and client overrides](/controls/parameters). |
| Review what changes Alignr may make. | **Standards → Run checks**, in the client approval-limit step. |
| Prepare external client access and presentation. | Client → **Client portal**. |
| Open reports, manual reviews or remediation history. | Client → **More**. |

The current client page does not expose a general **Edit client** form for changing its name, seats or PSA reference after creation. Review those fields when creating the client; use the specific settings below for connection, assessment and portal changes.

## Connect the client's tools

Under **Connections**, each assigned source has a site-access control. Microsoft connections call it **Client sites and access**; other connections call it **Client site access**. Open the control to see the sites linked to this client and, for Microsoft, the access check for the selected tenant. Choose **Link existing** to reuse a configured source: select its connection type and saved connection, refresh its sites if needed, compare the site name and identifier with the client's environment, then link the appropriate unassigned record. Nothing is linked until you choose a site. To set up a new source instead, choose **Add connection**.

Confirm **Assigned to this client**. If a site already belongs to another client, review its existing mapping before changing it through the integration's **Clients & sites** tab.

A shared connection can serve several clients through separate mappings. Several sites can belong to one client. The [mapping guide](/guides/organizations) explains how to keep those identities straight.

For Microsoft, select **Add Microsoft connection** to set up Direct access for the client, or **Link Partner Center connection** to choose an existing partner account and customer. After a Microsoft connection is assigned, open **Client sites and access** to inspect its linked sites and the client's tenant access. Your workspace may default to Partner Center while a client uses Direct because it has no suitable partner relationship. Follow [Microsoft connections for each client](/guides/client-microsoft-connections) for the exact steps.

## Choose domains to check

Open the client's **Domains** tab. Review **Discovered domains**, which lists verified custom domains from the selected Microsoft connection, and untick any you want to leave out. Add other client-owned domains under **Manual domains**, one per line.

Use **Run domain checks** to enable or pause scheduled checks, then select **Save settings**. When checks are enabled, domains are saved and there are no unsaved changes, use **Check now** to request a check.

These checks inspect public DNS for SPF, DMARC, MX and nameservers. They do not perform port scanning or prove that every aspect of email security is correctly configured. Use the [email and domain baseline](/controls/baselines/email) to understand the automated observations and separate human reviews.

For scheduling, target limits and recovery, see [Check client domains](/guides/domain-checks).

## Set expectations and approval limits

Choose a reviewed standard, check the client's coverage and record deliberate [client overrides](/controls/parameters) when its agreed thresholds differ. A connection preference chooses the source of evidence; a control parameter chooses the expectation applied to it.

The **Run checks** wizard also lets you review **Changes Alignr may make** for each selected client. Changing this option saves immediately; it does not wait for the final run confirmation. You need `organization.write` to change the client limit.

The client limit is one input to the effective permission to act. The control's limit, workspace limit and platform safety limit can reduce it. Alignr uses the most restrictive level, and irreversible work still requires a named human approver. See [remediation](/guides/remediation) before increasing it.

## Prepare the client portal separately

Open **Client portal** from the client page. This is an internal preview; it does not prove that an external person can sign in.

- **Sign-in access:** confirm the client's Microsoft tenant and choose the **Sign-in policy**, then **Save access settings**.
- **People & views:** configure each person's access and assigned view.
- **Content & presentation:** review what you will share.
- **Overview:** inspect the internal preview.

The sign-in choices are **Off — nobody can sign in**, **Only people explicitly granted access**, and **Everyone in this Microsoft tenant**. Under the last option, removing one person's explicit grant does not prevent them from signing in through the tenant-wide policy.

Viewing the portal requires client and portal access; changing the sign-in policy requires `organization.write`. Portal sign-in settings and Microsoft evidence connections are separate: authorising evidence collection does not automatically grant the client's people portal access.

## Your client is ready for an assessment when

You can identify its source mappings, explain the selected Microsoft method if applicable, inspect current observations and name the standard you intend to evaluate. Any client overrides or approval limits should be deliberate and understood.
