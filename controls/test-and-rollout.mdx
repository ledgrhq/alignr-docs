---
title: "Test and roll out a control"
description: "Check that a control asks the right question before relying on its results."
---

A syntactically valid definition can still ask the wrong question. Test the population, comparison and explanation, then assess whether your connected sources can support the conclusion. For grouped conditions, test each branch and the cases where evidence is missing or stale.

## Use four evidence cases

For the encryption example in [Create a custom control](/controls/create-custom):

| Case | Evidence | What to verify |
| --- | --- | --- |
| Satisfying | MDM enrolment and encryption `true` on the same subject. | The comparison is satisfied using eligible current evidence. |
| Contrary | MDM enrolment and encryption `false`. | The subject fails and the explanation cites the contrary observation. |
| Unknown | MDM enrolment with no encryption observation. | It does not pass; the missing observation is visible. |
| Empty population | No MDM enrolment observations. | No data is not presented as universal compliance. |

Also inspect mixed populations: a known failure can make the control fail while other subjects remain unknown. Failure does not imply complete evidence coverage.

## Check the boundaries

- Try the threshold itself and values on either side. “At most five” includes five.
- Confirm Boolean, numeric and text values are not being confused.
- Inspect excluded and filtered-out subjects, not just the ones that remain.
- Review observation time, source eligibility and stale evidence handling.
- Check the same subject is used across sources; a similar display name is insufficient.
- Review client overrides and the disabled state of the control and its parent standard.

## Preview the definition for one client

The control editor can run a read-only **Preview against a client** using a client in the standard's current scope. Choose **Preview client**, then **Preview conditions** after the required control details are complete. The request evaluates the current unsaved expected-condition tree for that one client. When editing a saved control, the preview also uses that client's saved parameter and source overrides; for a new control it uses the declared parameter defaults and connected, mapped sources.

Read the result as a bounded snapshot, not as a saved assessment. The preview can show an overall pass or fail, no data, not covered, or an incomplete result, with subject counts, decisive condition paths, missing predicates and source gaps. A true `any` branch can decide a result without every alternative being available. The preview does not collect fresh evidence, change the saved control, write a control evaluation or publish detections. A preview is specific to the selected client's current evidence; it does not establish how another client would evaluate.

The app needs client and control read access plus control write and fact read access to load the picker and preview. The preview request itself requires `detection_rule.write` and `fact.read`; the fact-read permission prevents the preview from becoming a way to inspect arbitrary client predicates without authority. For the request and response fields, see [Preview a custom control definition with the API](/api-reference/preview-control-definition).

## Roll out in a reviewable sequence

<Steps>
  <Step title="Prepare an editable draft">Copy a suitable library template or create a standard. Library copies start disabled; clear Enabled when drafting an individual custom control.</Step>
  <Step title="Check evidence coverage">Use the editor preview for an authorised client or an agreed representative workspace. Confirm the relevant integrations are connected, mapped and supplying the required predicates; review every reported source gap.</Step>
  <Step title="Inspect the definition and settings">Review scope, filters, each All/Any branch, thresholds and autonomy with the person responsible for the standard. Reopen the saved control and verify the tree and order persisted.</Step>
  <Step title="Enable deliberately and run checks">Account for the standard's scope and client overrides before enabling it. Use Run checks and inspect the resulting assessments, evidence and evaluation time.</Step>
  <Step title="Review the wider impact">Investigate unexpected failures and gaps before relying on the standard across clients. Document intentional exceptions and identify who handles follow-up.</Step>
</Steps>

Use real observations in a test workspace or an agreed client context. Keep synthetic examples out of production evidence.

## Recheck after changes

Repeat the relevant cases when predicates, source normalisation, filters, operators, defaults or client overrides change. A past result answers the previous question using the evidence available then.

Keep automated assessment and remediation separate. An enabled control does not guarantee a supported automatic fix. See [remediation and approvals](/guides/remediation).
