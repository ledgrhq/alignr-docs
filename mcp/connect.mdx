## Before you begin

You need a client supporting remote Streamable HTTP servers and an [Alignr API key](/guides/api-keys). In the app, open **MCP → + Generate token** and create a user key with the `organization:read` scope to test a read-only tool. Copy it when shown; Alignr does not display its value again. You can call `list_organizations` to find a client ID. An Organization represents one of your MSP’s clients.

## 1. Add the server

Use these values in your client’s remote MCP settings:

```text
Name: Alignr
URL: https://api.alignr.io/mcp/
Transport: Streamable HTTP
Header: Authorization: Bearer <your-api-key>
```

Clients use different configuration formats and secret-storage mechanisms. If your client accepts an `mcpServers` configuration with `url` and `headers`, the shape is:

```json
{
  "mcpServers": {
    "Alignr": {
      "url": "https://api.alignr.io/mcp/",
      "headers": {
        "Authorization": "Bearer <your-api-key>"
      }
    }
  }
}
```

Replace the placeholder using your client’s protected credential mechanism. Do not commit a configuration containing a real key. Clients that support only local stdio processes cannot connect directly with this configuration.

## 2. Discover help and verify a read

Reconnect the server in your client. If it supports MCP resources, open its resource browser or ask it to list resources and read `alignr://help/getting-started` with `resources/read`. Read `alignr://help/tools-and-scopes` for the server's registered tools, scopes and required owner permissions. A valid bearer key is required for both resources, but they need no extra tool scope. If your client does not expose resources, use this guide and the [tool catalogue](/mcp/tools) instead.

Inspect the discovered tools with `tools/list`, then ask the client to call `get_organization` with the ID of an Organization you can access. Confirm the returned client matches your intended target. Resource discovery and tool discovery do not authorise a tool call; its scope and the key owner's current permissions are checked when it runs.

For the control-results example below, create a replacement key with `compliance:read` and `compliance:explain`. Keep `organization:read` if you also want to look up the client. Scopes are fixed when a key is created.

## 3. Ask about a control result

After connecting, begin with a bounded read request such as:

> For this Organization ID, retrieve its compliance results and explain one failing control. Include the control identifier and the evidence behind the explanation. Do not make changes.

Grant only the scopes required by the tools involved. For this workflow, consult `get_organization_compliance` and `explain_control_status` in the [tool catalogue](/mcp/tools).

A useful answer identifies the client, the expectation, the actual observation and what remains unknown. If the answer says “MFA registered”, do not read that as “MFA enforced everywhere”. Use the [predicate guide](/guides/predicates) to check the claim.

## Choose the tool for the question

| Question | Tool to inspect |
| --- | --- |
| Which client is this ID? | `get_organization` |
| Which clients do I manage? | `list_organizations` |
| What is this client's control posture? | `get_organization_compliance` |
| Why does one control have this result? | `explain_control_status` |
| Which clients have a particular control status? | `list_organizations_by_control_status` |
| How do clients stand against a standard? | `get_standard_rollup` |
| What findings are open? | `list_detections` |
| What kind of steps does a proposed remediation plan contain? | `get_remediation_plan_outline` — requires `remediation:read`; metadata only. |
| What is the status of a remediation run? | `list_remediation_runs` or `get_remediation_run_status` — requires `remediation:read`; neither confirms rollback eligibility. |
| Can I add an agreed note to a finding? | `create_detection_note` — requires write access. |

Tool availability and permission checks remain server-side. A client's ability to discover a tool is not permission to execute it.

For an assistant such as Claude Code or Codex, use `get_remediation_plan_outline` to explain the broad intent of an existing plan identified by UUID. The outline gives action types and approval/reversibility metadata, not step parameters, targets, simulation mode or execution readiness. If an action was already requested, use `list_remediation_runs` or `get_remediation_run_status` to report its lifecycle and separate verification state. A run marked completed does not prove the control is fixed. To inspect live target choices, authority and the full plan, or to request, approve or roll back an action, continue in the signed-in [remediation workflow](/guides/remediation) with the appropriate human permissions. These MCP reads do not perform those actions.

For client creation and updates, follow [Manage clients with MCP](/mcp/manage-clients) and issue a separate user-owned key with the required write scope.

## Codex

Set `ALIGNR_MCP_TOKEN` through your local secret-management environment, then add this entry to `~/.codex/config.toml`:

```toml
[mcp_servers.alignr]
url = "https://api.alignr.io/mcp/"
bearer_token_env_var = "ALIGNR_MCP_TOKEN"
```

Codex reads the token from that environment variable and sends it as a bearer token. See the [Codex MCP configuration reference](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) for current client settings.

## Claude Code

Set `ALIGNR_MCP_TOKEN` in Claude Code's environment and add this entry to a project `.mcp.json` or your user-level Claude Code MCP configuration:

```json
{
  "mcpServers": {
    "alignr": {
      "type": "http",
      "url": "https://api.alignr.io/mcp/",
      "headers": { "Authorization": "Bearer ${ALIGNR_MCP_TOKEN}" }
    }
  }
}
```

Claude Code expands the variable in HTTP headers. See the [Claude Code MCP configuration guide](https://code.claude.com/docs/en/mcp) for configuration scopes and current client settings.

These examples use user-owned bearer keys. They do not imply support for clients that require an OAuth authorisation flow. Alignr rechecks the key and its owner’s current permissions on each request, including requests made through an already connected client.

## Troubleshoot

- **Unauthorised:** check the bearer header, key expiry and revocation.
- **Tool denied:** check both the assigned scope and the key owner’s current permissions.
- **Not found:** confirm the endpoint, server availability and Organization ID.
- **No tools:** confirm Streamable HTTP support and that the server is enabled using the [live reference](/api-reference/live-schema).
