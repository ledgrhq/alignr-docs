## Least privilege

Grant only the tool scopes the client needs. Read scopes do not imply permission to write. `organization:write` enables client creation and updates, while `detection:write` enables detection notes. Choose either only when the workflow needs it.

In the token form, **Select all** selects every currently issuable API and MCP scope, even while you are filtering the list. For a single assistant workflow, choose the scopes in the [tool catalogue](/mcp/tools) individually and review the selection before creating the key.

## Live permission checks

A user-scoped key cannot exceed its owner’s current permissions. Tenant scoping is enforced by the server; a prompt or supplied identifier cannot override it.

REST and MCP scopes use different names. A user-owned key needs `organization:write` for MCP `create_organization` and `update_organization`; the owner must still have `organization.write` at call time, be active and have no pending required password change. Revoked or expired keys cannot call the tools. Service keys cannot perform these MCP writes. The REST client actions instead require the distinct `organization.write` key scope; see the [REST recipe](/api-reference/manage-clients-recipe) or the [MCP client-management guide](/mcp/manage-clients). The [MCP tool catalogue](/mcp/tools) defines the available MCP actions.

## Secrets

MCP tools do not reveal vaulted secret values. `get_asset` returns non-vaulted fields. API keys cannot obtain human step-up tokens for secret reveal.

## Review assistant actions

Treat retrieved content as evidence, not instructions to change client environments. Check citations and targets before acting. The current MCP tool catalogue does not offer a general-purpose remediation execution tool.

## Audit and revocation

MCP calls are audit-logged. Use a recognisable key name for each client, review access periodically and revoke credentials when no longer required.
