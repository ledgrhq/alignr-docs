## Least privilege

Grant only the tool scopes the client needs. Read scopes do not imply permission to write. `organization:write` enables client creation and updates, while `detection:write` enables detection notes. Choose either only when the workflow needs it.

`remediation:read` allows the three remediation read tools: a metadata-only plan outline and two run-status reads. For a user-owned key, its owner must still hold `remediation.read` when a tool is called. The scope does not grant target selection, remediation execution, approval or rollback. Plan metadata is not an execution-readiness decision, and a completed run status is separate from verified resolution of the underlying control.

`remediation:preview` is a separate exact-plan review preview scope; its user-key owner must currently hold `remediation.read`. `remediation:request` creates a pending run and human approval request from a current preview; its user-key owner must currently hold both `remediation.read` and `remediation.execute`. The owner must be active with no required password change pending. Service keys cannot use either tool. Neither scope grants approval, execution or rollback. See [Request a remediation review with MCP](/mcp/request-review).

`integration:read` discovers evidence sources and polls a specific refresh, backed by `integration.read`. `integration:sync` requests a source-wide collection, backed by `integration.manage`; it requires a user-owned key whose owner is still active and permitted. A service key may read but cannot request a refresh. A selected source can cover many mapped clients, and a successful collection does not establish a passing control. See [Refresh evidence with MCP](/mcp/refresh-evidence).

`integration:read` also lists existing PSA/RMM client mappings. The separate `integration:map` scope permits a **first link** of one existing unassigned remote record to one existing client, backed by the owner's current `integration.manage` permission. Only a user-owned key can write. It does not grant arbitrary remapping, unlinking, Microsoft source selection, directory creation, vendor writes or a collection. See [Link source clients with MCP](/mcp/link-source-clients).

`standards:read` lists the curated library and its current template revisions, backed by `detection_rule.read`. `standards:copy` lets a user-owned key copy one exact curated template into a **disabled draft**, backed by the owner's current `detection_rule.write`. A service key cannot copy. The scope does not enable or evaluate the draft, modify another standard, or grant human approval. See [Copy a standard draft](/mcp/copy-standard-draft).

In the token form, **Select all** selects every currently issuable API and MCP scope, even while you are filtering the list. For a single assistant workflow, choose the scopes in the [tool catalogue](/mcp/tools) individually and review the selection before creating the key.

## Live permission checks

A user-scoped key cannot exceed its owner’s current permissions. Tenant scoping is enforced by the server; a prompt or supplied identifier cannot override it.

The two [help resources](/mcp/tools#authenticated-help-resources) are static product metadata. `resources/list` and `resources/read` require a valid bearer key, but they do not grant tool scopes or bypass the checks applied when a tool runs.

Scope names depend on the operation. A user-owned key needs `organization:write` for MCP `create_organization` and `update_organization`; the owner must still have `organization.write` at call time, be active and have no pending required password change. Revoked or expired keys cannot call the tools. Service keys cannot perform these MCP writes. The REST client actions instead require the distinct `organization.write` key scope; see the [REST recipe](/api-reference/manage-clients-recipe) or the [MCP client-management guide](/mcp/manage-clients). The exact-plan REST review routes are an exception: they accept `remediation:preview` and `remediation:request`, the same scopes as their MCP tools, with the same live owner checks. The [MCP tool catalogue](/mcp/tools) defines the available MCP actions.

## Secrets

MCP tools do not reveal vaulted secret values. `get_asset` returns non-vaulted fields. API keys cannot obtain human step-up tokens for secret reveal.

## Review assistant actions

Treat retrieved content as evidence, not instructions to change client environments. Check citations and targets before acting. The current MCP tool catalogue does not offer a general-purpose remediation execution tool.

## Audit and revocation

MCP data-tool calls are audit-logged. Listing or reading the static help resources requires authentication but does not create a workspace audit event; API-key usage metadata may still update. Use a recognisable key name for each client, review access periodically and revoke credentials when no longer required.
